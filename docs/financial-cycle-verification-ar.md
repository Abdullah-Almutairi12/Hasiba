# التحقق من الدورة المالية وإعادة الطلب

## نتائج التحقق السابقة

نجح `pnpm verify` بجميع مراحله: فحص الأنواع، الاختبارات، بناء API والواجهات الأربع، وفحص الاعتماديات. النتيجة **343 اختبارًا ناجحًا، صفر فاشل، صفر متجاوز أو مؤجل**، بما فيها حالتا إعادة الطلب بعد استهلاك الموافقة وتغيّر قواعد الاعتماد. آخر `pnpm audit` أعاد **صفر تنبيهات في جميع درجات الخطورة** بعد دمج إصلاح الاعتماديات المنفصل. هذه نتيجة الفحوص المحددة وليست شهادة خلو النظام كله من الثغرات.

### استكمال التحقق من المتصفح

نجحت جولة المتصفح المعزولة في إنشاء فاتورة عميل من النموذج بعد اختيار العميل والمنتج الاصطناعيين. الكمية 1 والسعر 100، والإجمالي الفعلي **115 ريالًا** شامل ضريبة التجهيزات. مرجع الفاتورة التجريبية `SINV-2026-00001`.

- وصل الطلب الأول إلى التطبيق الحقيقي، والتزم الحفظ وأعاد التطبيق 201. قطع الوكيل الرد قبل إرساله للمتصفح؛ عرضت الواجهة `HTTP 502` وبقي النموذج مفتوحًا بالقيم نفسها.
- أُعيد الضغط على «حفظ» دون تعديل. سجّل الوكيل طلبًا ثانيًا بالمفتاح وبصمة الجسم نفسيهما، وردًّا 201 مع `Idempotency-Replayed: true` ومعرّف الفاتورة ومرجعها نفسيهما.
- بعد كل محاولة: **فاتورة واحدة وإيصال إعادة طلب واحد** في القاعدة المعزولة.
- ظهرت رسالة «تم إنشاء الفاتورة»، وأُغلق النموذج وتحدّثت القائمة. بقي الصف نفسه مرة واحدة بعد إعادة فتح قائمة الفواتير وبعد إعادة تحميل المتصفح كاملة.

الأدلة الآلية في `generated-artifacts/verification/browser-retry-proxy.json`، وتقرير المتصفح ولقطاته في `generated-artifacts/verification/financial-browser-results.json`. لم تُستخدم بيانات التطبيق، ولم يضف الاختبار مسار إنتاج أو تجاوز تسجيل دخول. هذه الجولة تستكمل الدليل السابق؛ لا تعني إعادة تنفيذ كل الاختبارات المذكورة أعلاه.

### التحقق من إعادة التحميل قبل تأكيد الحفظ — 2026-10-22

نجحت جولة متصفح جديدة على قاعدة مؤقتة من `node scripts/test-isolated.mjs --browser` وبالوكيل الاختباري نفسه. استُخدم تسجيل الدخول العادي للمالك الاصطناعي، ومنتج وعميل التجهيزات فقط، بكمية 1 وسعر 100 وخصم صفر وملاحظات فارغة؛ الإجمالي المشاهد 115 ريالًا.

- التزم الطلب الأول وأعاد API الحالة 201، ثم قُطع الرد قبل وصوله إلى المتصفح. ظهرت رسالة عدم تأكد وبقي النموذج مفتوحًا. أثبت تقرير الوكيل وجود فاتورة واحدة وإيصال إعادة طلب واحد قبل إعادة التحميل.
- التُقط مفتاح `sessionStorage` بعد الفشل، ثم أُعيد تحميل الصفحة في التبويب نفسه **قبل إعادة المحاولة**. أثبتت لقطة المتصفح `navigationType: "reload"` وارتفاع `timeOrigin` من `1792635024152.4` إلى `1792635129644.5`، مع بقاء اسم المفتاح وقيمته نفسيهما.
- فُتح نموذج جديد وأُعيد إدخال البيانات الاصطناعية نفسها يدويًا. نتج عن الضغط على «حفظ» طلب ثانٍ بالمفتاح وبصمة الجسم نفسيهما؛ أعاد API الحالة 201 مع `Idempotency-Replayed: true` والفاتورة ذات المعرّف 1 والمرجع `SINV-2026-00001`.
- بقي العدد بعد المحاولتين **فاتورة واحدة وإيصالًا واحدًا**، وظهر المرجع الأصلي في القائمة مرة واحدة. ظهرت رسالة «تم إنشاء الفاتورة»، وأُغلق النموذج، وأصبح عدد مفاتيح العمليات المالية في الجلسة صفرًا في المستند المعاد تحميله نفسه.

نجح `node scripts/check-browser-retry.mjs` على أدلة الجولة الفعلية، ونجحت اختبارات حارس الأدلة الـ18، وفحص أنواع API. شغّل فحص الإكمال `pnpm run verify` لاحقًا: نجح فحص الأنواع و**372 اختبارًا دون فشل أو تجاوز** وبناء API والواجهات الأربع. لم ينجح الأمر الشامل بسبب تعذر خدمة تدقيق الاعتماديات: أعادت نقطة الفحص الخارجية 502، ثم انتهت إعادة محاولة مرحلة التدقيق وحدها بمهلة اتصال. **فحص الاعتماديات الحالي غير مكتمل**؛ نتيجة التدقيق السابقة أعلاه ليست بديلًا عنه. لم تُغيّر الاعتماديات أو شروط الفحص لتجاوز ذلك.

الأدلة المحلية (ضمن مجلد المخرجات المستبعد من Git):

- `generated-artifacts/verification/browser-retry-proxy.json`: التزام الطلبين، المفتاح والبصمة وهوية الفاتورة والأعداد.
- `generated-artifacts/verification/browser-retry-reload.json`: لقطات التخزين والتوقيت قبل إعادة التحميل وبعدها وبعد النجاح، مرتبطة بمعرّف جولة الوكيل.
- `generated-artifacts/verification/financial-browser-reload-results.json`: تقرير المشاهدة المنقّح.
- `generated-artifacts/verification/financial-browser-reload-screenshots/`: خمس لقطات للنتيجة غير المؤكدة وإعادة التحميل وإعادة الإدخال والنجاح والقائمة النهائية.

لم يُغيّر الاختبار مسارات الإنتاج أو المصادقة أو سلوك التطبيق. لا يُحفظ جسم الفاتورة أو كلمات المرور في أدلة النقل. أُوقف الوكيل ثم مشغّل الاختبار بإيقاف منظّم؛ تأكد حذف ملف الحسابات الاصطناعية ومجلد القاعدة المؤقتة، وأُعيد تشغيل سير عمل API المعتاد وتأكدت جاهزيته من سجل التشغيل.

## تعريف العملية المكررة

يعرّف `Idempotency-Key` نية مالية واحدة ضمن **الشركة المصرح بها، والمستخدم، ومسار العملية**. المفتاح نفسه والبيانات نفسها يسترجعان نتيجة العملية السابقة دون إنشاء فاتورة أو حركة أو قيد جديد. إعادة المفتاح مع بيانات مختلفة ترفض بـ409. مفتاحان مختلفان يسمحان بعمليتين مشروعتين ولو كانت بياناتهما متساوية.

تُحفظ نتيجة المعاملة وبصمة المدخلات في `financial_requests` داخل معاملة PostgreSQL نفسها. قفل معاملات استشاري يسلسل الطلبات المتزامنة للمفتاح نفسه؛ فشل المعاملة يلغي بياناتها وإيصال إعادة الطلب معًا. لا تعتمد هذه الحماية على ذاكرة خادم واحد. لا يُحذف الإيصال تلقائيًا مع الزمن، لأن إعادة طلب قديم بعد حذفه قد تنشئ عملية أخرى.

المفتاح اختياري للتوافق مع العملاء السابقين. يجب على أي عميل خارجي يريد ضمان إعادة المحاولة استخدامه. لا يمكن استنتاج نية التكرار بأمان من تشابه بيانات فاتورتين.

## المسارات المغطاة

- إنشاء فواتير العملاء وعكسها وسندات القبض والإشعارات الدائنة.
- إنشاء أوامر الشراء واستلام البضاعة.
- إنشاء فواتير المورد اليدوية، واعتماد نتيجة المسح وعكس فاتورة المورد.
- إنشاء طلب نقطة البيع والحركة اليدوية للمخزون.

مسح الصورة نفسه، إرسال البريد، إنشاء رابط دفع، واستدعاءات بوابات الدفع ليست ضمن هذا الضمان. لا تتعامل الاختبارات مع بوابات حقيقية.

الإشعار الدائن يظل مسارًا على مرحلتين متوافقًا مع الاعتمادات: إنشاء مسودة محفوظة ثم الإصدار. إعادة الطلب تستأنف المسودة نفسها، وإصدارها يقفل رأسها ويرجع المستند الحالي إن كان صادرًا بالفعل. فشل الإصدار لا يترك قيدًا أو حركة مخزون جزئية، لكنه قد يترك مسودة قابلة للاستئناف. المسودات والطلبات المعلقة تحجز كمية المرتجع حتى لا تتجاوز طلبات متزامنة الكمية المباعة.

## سلوك الواجهة

`apiPost` وعميل API المولد واعتماد فاتورة المورد من المسح تستخدم `financialFetch`. يُحفظ مفتاح عشوائي مع بصمة الطلب في تخزين الجلسة، لا جسم الفاتورة أو بيانات الاعتماد. الطلبات المتزامنة المتطابقة تشترك في المفتاح. انقطاع الاتصال، وخطأ الوكيل 5xx، أو رد ناجح غير قابل للقراءة تُبقي المفتاح للطلب التالي. بعد نجاح مؤكد تصبح الإرسالية التالية عملية جديدة.

تظهر عند النتيجة غير المؤكدة رسالة تطلب إعادة المحاولة بالبيانات نفسها. إذا تعذر تخزين المفتاح لا يُرسل الطلب المالي. لا تغيّر البيانات لتجاوز رسالة الانقطاع قبل مراجعة نتيجة العملية السابقة؛ البيانات المختلفة تعني نية أخرى.

## العيوب المثبتة والإصلاحات

1. **فهرس المخزون غير متطابق:** تعريف Drizzle القديم استخدم أعمدة lot/variant القابلة للفراغ مباشرة، بينما `ON CONFLICT` في دفتر المخزون يعتمد `COALESCE`. وُحّد التعريف والترحيل مع صيغة الدفتر. إذا وجدت أرصدة تاريخية متكررة يفشل إنشاء الفهرس؛ لا تُدمج الأرصدة ولا تُحذف تلقائيًا.
2. **فحص فاتورة المورد خارج المعاملة:** كان يُنفذ قبل قفل سجل إعادة الطلب، فيرفض إعادة اعتماد فاتورة ناجحة، ويتيح التسابق على الكميات المفوترة. انتقل الفحص داخل المعاملة مع قفل أمر الشراء وجمع الكمية المطلوبة للبنود التي تعيد السطر نفسه.
3. **التسابق على إنشاء التسلسلات:** `CREATE SEQUENCE IF NOT EXISTS` وحده لا يمنع تصادم إنشاء أول تسلسل متزامن. أضيف قفل عند غياب التسلسل فقط. أرقام طلبات POS تتضمن لاحقة عشوائية بدل الاعتماد على المللي ثانية وحدها.
4. **تكرار إصدار المرتجع:** أضيف قفل رأس الإشعار وإرجاع النتيجة الحالية عند إعادة إصداره، وحجز كميات المسودات والمعلقات مع التحقق التراكمي للبنود.
5. **ترحيل تكلفة المرتجع:** إعادة المخزون كانت لا تعكس تكلفة البضاعة المباعة في الدفتر المالي. يضيف الإصدار مدين المخزون ودائن تكلفة البضاعة بقيمة حركة الإرجاع، ضمن المعاملة نفسها.
6. **قيم القيود غير الصالحة:** تُرفض قيم `NaN`/`Infinity` وسعر صرف غير موجب أو غير محدود قبل كتابة القيد.
7. **موافقة POS أحادية الاستخدام:** أصبح استرجاع نتيجة الطلب الملتزم سابقًا يسبق التحقق من الموافقة المستهلكة. الطلب الجديد لا يتجاوز فحص الموافقة، ويقفلها ويستهلكها داخل معاملة البيع نفسها.
8. **تغيّر سياسة اعتماد المرتجعات:** يُقرأ وضع الإشعار الحالي قبل إعادة تقديمه للاعتماد، ولا يمكن لتحديث حالة مشروط إعادة إشعار صادر إلى `pending_approval`. إضافة قاعدة اعتماد بعد الإصدار لا تنشئ اعتمادًا أو قيدًا أو مخزونًا جديدًا عند إعادة الطلب.

## الاختبارات

الأمر الكامل:

```bash
pnpm verify
```

اختبارات هذه الإضافة فقط، على عنقود PostgreSQL جديد ومؤقت:

```bash
pnpm test:isolated src/routes/financial-cycle.test.ts test/financial-fetch.test.mjs
```

السيناريوهات:

- أمر شراء واحد لطلبين متزامنين بالمفتاح نفسه.
- استلام البضاعة وقيد GR-IR مرة واحدة رغم إعادة الطلب.
- رفض تجميع بنود فاتورة مورد بما يتجاوز المستلم؛ إعادة استخدام المفتاح بعد فشلها تسمح بالطلب المصحح.
- فاتورة مورد مرتبطة بالاستلام، إعادة اعتمادها، وعكسها تحت طلبين متزامنين.
- بيع POS وحركاته وفاتورته وقبضه مرة واحدة.
- مرتجع مبيعات متزامن بمفتاحين مختلفين؛ قبول واحد ورفض تجاوز الكمية، وإعادة ناجحة دون زيادة المخزون.
- مصالحة رصيد المخزون المالي وCOGS في دورة التكلفة الثابتة المختبرة.
- فاتورتان متطابقتان مشروعًا بمفتاحين مختلفين؛ واسترجاع إحداهما دون تكرار، ورفض تغيير البيانات تحت مفتاحها.
- فشل بند استلام متأخر يلغي الاستلام السابق وحركته وقيده؛ وطلبان مختلفان على المتبقي لا يزيدانه.
- رفض POS ناقص المخزون دون فواتير أو قيود أو طلبات يتيمة.
- تكرار حركة مخزون يدوية.
- تساوي المدين والدائن لكل قيد مرحّل، وتراجع قيد مكتوب عند فشل معاملته الخارجية.
- رفض قيد غير متوازن وقيم مالية غير صالحة.
- قبول طلبي POS مشروعين متزامنين بأرقام مختلفة.
- إسقاط نتيجة POS الملتزم من منظور المستدعي ثم إعادة جسم الطلب ومفتاحه بعد استهلاك الموافقة: يرجع الطلب السابق دون تكرار؛ مفتاح جديد مع الموافقة المستهلكة يُرفض.
- تفعيل قاعدة اعتماد جديدة بعد إصدار مرتجع ثم إعادة طلبه مرتين: تبقى حالته وقيده والمخزون وعدد طلبات الاعتماد كما كانت.
- اختبارات النقل للواجهة: التزامن، انقطاع الاتصال، 5xx، رد ناجح تالف، وانعدام تخزين الجلسة.

التقارير الفعلية وأعداد النجاح/الفشل/التجاوز في:

- `generated-artifacts/verification/summary.json`
- `generated-artifacts/verification/tests.json`
- سجلات المراحل في المجلد نفسه.

ملف اختبارات النقل بصيغة JavaScript خارج مشروع TypeScript الخاص بالخادم، ليظل الكود ذو أنواع DOM ضمن مشروع عميل الويب الصحيح. كود النقل نفسه يبقى TypeScript ويخضع لفحص مكتبة العميل؛ لم يُعطل فحص أنواع التطبيق.

## إعادة اختبار فقد الرد من المتصفح ببيانات معزولة

1. شغّل `node scripts/test-isolated.mjs --browser` وانتظر رسالة جاهزية التجهيزات. تُنشأ قاعدة مؤقتة جديدة وحسابات وعميل ومنتج اصطناعية فقط؛ تُحذف القاعدة عند إيقاف المشغّل أو انتهاء مهلة 15 دقيقة.
2. أوقف سير عمل API المعتاد مؤقتًا، واترك واجهة ERP تعمل. لا تشغّل API المعتاد على قاعدة التطبيق أثناء الجولة.
3. شغّل الوكيل الاختباري:

   ```bash
   pnpm --filter @workspace/scripts exec tsx ../artifacts/api-server/src/test/browser-retry-proxy.ts
   ```

   يقرأ الوكيل حالة الاختبار من `/tmp/hasba-browser-state.json`، ويرفض عنوان قاعدة غير محلي أو اسم قاعدة غير مخصص للاختبار. يشغّل التطبيق الحقيقي دون عمّال التكاملات، ويستقبل الطلبات عبر منفذ API المعتاد. لا يضيف مسارًا للتطبيق أو تجاوزًا لتسجيل الدخول. **أوقفه قبل إعادة تشغيل API المعتاد.**
4. في متصفح بجلسة جديدة، سجّل الدخول بالطريقة العادية بحساب المالك الاصطناعي من ملف الحالة. افتح المبيعات ← فواتير العملاء ← فاتورة جديدة. اختر العميل التجريبي و«منتج اختبار»، بكمية 1 وسعر 100، ثم احفظ.
5. يقطع الوكيل أول رد ناجح لإنشاء فاتورة عميل **بعد اكتمال الرد من التطبيق والتزام المعاملة**، دون إرسال بايتات النجاح للمتصفح. لا تضغط «حفظ» مرة ثانية الآن:
   - انتظر ظهور النتيجة غير المؤكدة، وتحقق من سجل الوكيل: نجاح API، و`dropped: true`، وفاتورة واحدة وإيصال واحد.
   - التقط `beforeReload` من المتصفح بالكود أدناه. يجب أن يوجد مفتاح مالي واحد.
   - أعد تحميل الصفحة فعلًا في **التبويب نفسه**؛ لا تفتح جلسة جديدة ولا تكتفِ بالتنقل بين صفحات التطبيق.
   - بعد اكتمال التحميل وقبل أي حفظ، التقط `afterReload`. يجب أن يبقى اسم مفتاح الجلسة وقيمته دون تغيير، ويزداد `timeOrigin` ويصبح `navigationType` مساويًا لـ`reload`.
   - افتح «فاتورة جديدة» وأعد إدخال **نفس** العميل والمنتج والكمية والسعر والخصم والملاحظات والقيم الافتراضية؛ لا يُفترض أن التطبيق يسترجع حقول النموذج تلقائيًا. احفظ مرة واحدة.
   - بعد رسالة النجاح وإغلاق النموذج وظهور المرجع الأصلي مرة واحدة، التقط `afterSuccess`. يجب أن تكون قائمة المفاتيح المالية فارغة. أضف إلى هذه اللقطة `formClosed` و`visibleInvoiceCount` و`reference` من المشاهدة الفعلية للقائمة.

   كود اللقطة (قراءة فقط، لا يرسل طلبًا ولا يغيّر التخزين):

   ```js
   ({
     observedAt: Date.now(),
     timeOrigin: performance.timeOrigin,
     navigationType: performance.getEntriesByType("navigation")[0]?.type,
     entries: Object.entries(sessionStorage)
       .filter(([name]) => name.startsWith("hasba:financial-request:")),
   })
   ```

   احتفظ باللقطات خارج الصفحة قبل إعادة تحميلها. احفظ ملف `generated-artifacts/verification/browser-retry-reload.json` بالشكل `{ runId, beforeReload, afterReload, afterSuccess }`، حيث `runId` من تقرير الوكيل **للجولة نفسها**. لا تُنسخ كلمات المرور أو الكوكيز أو بقية تخزين المتصفح. تكون اللقطة الأخيرة مثل `{ observedAt, timeOrigin, navigationType, entries: [], formClosed: true, visibleInvoiceCount: 1, reference: "المرجع المشاهد" }`.
6. افحص دليل الطلبين:

   ```bash
   node scripts/check-browser-retry.mjs
   ```

   يفحص تطابق المفتاح وبصمة الجسم ومعرّف الفاتورة ومرجعها، ووجود `Idempotency-Replayed` في المحاولة الثانية، وعدد الفواتير وإيصالات إعادة الطلب بعد كل محاولة. ويرفض دليلًا من جولة أخرى أو إعادة تحميل بعد النجاح فقط أو إعادة الحفظ من النموذج المفتوح دون تحميل. يطابق لقطات الجلسة مع المفتاح الفعلي واسم تخزينه المحسوب من المسار والجسم، ويتحقق من ترتيبها الزمني وتنظيف المفتاح وظهور المرجع مرة واحدة. التقرير في `generated-artifacts/verification/browser-retry-proxy.json` لا يخزن جسم الفاتورة أو كلمة المرور. هذا الفحص يكمل مشاهدة القائمة من المتصفح ولا يحل محلها.

   يمكن فحص حارس الأدلة نفسه دون قاعدة بيانات أو متصفح:

   ```bash
   node --test scripts/check-browser-retry.test.mjs
   ```

   هذه اختبارات اصطناعية لقبول ورفض الأدلة، وليست بديلًا لجولة المتصفح الفعلية.
7. أوقف الوكيل أولًا ثم مشغّل القاعدة المؤقتة، وأعد تشغيل سير عمل API المعتاد دون أي تجاوزات بيئية. لا تنقل ملف الحالة أو حسابات الاختبار إلى التطبيق.

## إنشاء فاتورة ثانية مطابقة بعد تأكيد استرجاع الأولى

هذا سيناريو مستقل من **ثلاثة طلبات** على نفس قاعدة الاختبار المؤقتة والوكيل أعلاه، بتسجيل دخول عادي بالحساب الاصطناعي. لا تُستخدم قاعدة التطبيق، ولا يُضاف مسار إنتاج أو تجاوز دخول.

1. نفّذ خطوات فقد الرد وإعادة التحميل واسترجاع الفاتورة الأولى أعلاه حتى `afterSuccess`: النموذج مغلق، المرجع ظاهر مرة واحدة، والمفاتيح المالية فارغة. احتفظ بدليل الطلبين قبل المتابعة؛ يبقى `checkBrowserRetry` ملزمًا بطلبين بالضبط.
2. افتح «فاتورة جديدة» **بعد** تأكيد النجاح. التقط `afterNewForm` بكود اللقطة أعلاه، وأضف `formOpen: true` بناء على مشاهدة النموذج. يجب أن تبقى المفاتيح المالية فارغة.
3. أدخل نفس العميل والمنتج والكمية والسعر والخصم والضريبة والملاحظات، ثم احفظ مرة واحدة. انتظر إغلاق النموذج وظهور مرجعين مختلفين، كل منهما مرة واحدة.
4. التقط `afterSecondSuccess` وأضف `formClosed: true` و`visibleInvoiceCount: 2` و`references` كمصفوفة المرجعين المشاهدين. احفظ `{ runId, beforeReload, afterReload, afterSuccess, afterNewForm, afterSecondSuccess }` في `generated-artifacts/verification/browser-identical-invoice.json`. انسخ تقرير الوكيل النهائي، دون تغييره، إلى `generated-artifacts/verification/browser-identical-invoice-proxy.json`.
5. شغّل:

   ```bash
   node scripts/check-browser-identical-invoice.mjs
   node --test scripts/check-browser-retry.test.mjs scripts/check-browser-identical-invoice.test.mjs
   ```

يفحص الحارس الجديد أول طلبين بالحارس الأصلي نفسه، ثم يشترط للطلب الثالث مفتاحًا جديدًا وبصمة جسم واسم تخزين مطابقين للأول، ونجاحًا غير معاد دون ترويسة `Idempotency-Replayed` حتى لو كانت قيمتها `false`. يشترط فاتورتين وإيصالين محفوظين بهويتين مختلفتين، مع بقاء الإيصال الأول وربط كل مفتاح بمعرّف فاتورته في قاعدة الاختبار. يسجّل الوكيل هوية الإيصال المركبة ومعرّف الفاتورة فقط، دون جسم الفاتورة أو بيانات الدخول.

الفحص الجديد لا يخفّف شرط الطلبين في `scripts/check-browser-retry.mjs`؛ تقرير الطلبات الثلاثة يُرفض فيه عمدًا. لا تستبدل تقرير السيناريو القديم بتقرير الثلاثة طلبات إذا أردت تشغيل فحصه المباشر. اختبارات قبول ورفض الأدلة ليست بديلًا عن تنفيذ السيناريو بالمتصفح.

يمكن التقاط ربط الإيصالات المحفوظة مجددًا **بالقراءة فقط وقبل إيقاف القاعدة المؤقتة**:

```bash
pnpm --filter @workspace/scripts exec tsx ../artifacts/api-server/src/test/browser-retry-proxy.ts --capture-receipts
```

يضيف هذا الأمر `finalReceipts` و`receiptsObservedAt` إلى تقرير الوكيل الموجود دون تعديل أحداث الطلبات أو تشغيل مستمع أو إرسال طلب حفظ. يرفض إذا لم تطابق هويات الإيصالات آخر حدث للجولة. يتطلب الحارس لقطة نهائية بعد الالتزام الثالث، بهويتي الإيصالين نفسهما وربط كل منهما بمعرّف فاتورته الصحيح. انسخ التقرير المحدّث إلى `browser-identical-invoice-proxy.json` قبل فحصه.

أوقف الوكيل ثم مشغّل القاعدة المؤقتة وأعد تشغيل API المعتاد كما في الخطوة الأخيرة أعلاه.

### نتيجة الجولة الفعلية — 2026-10-22

اكتملت الجولة من واجهة `/sales` ← «فواتير العملاء»، بتسجيل الدخول العادي للمالك الاصطناعي. فُقد الرد الأول بعد التزام `201`، واحتفظ التبويب بالمفتاح عبر إعادة تحميل حقيقية. أعاد الحفظ المتطابق الفاتورة `SINV-2026-00001` دون إنشاء نسخة. بعد إغلاق النموذج وتنظيف المفتاح فُتح نموذج جديد بالبيانات نفسها؛ أنشأ الحفظ الفاتورة `SINV-2026-00002` بمفتاح جديد ودون ترويسة إعادة. ظهرت الفاتورتان مرة واحدة لكل منهما، وسجّل الوكيل فاتورتين وإيصالين مختلفين.

كشفت الجولة خطأً في إسقاط معرّف الفاتورة من JSON الإيصال في وكيل الاختبار، وليس في الحفظ: يُغلّف الناتج داخل `value.inv`. صُحّح الاستعلام، وأُضيفت قراءة نهائية مستقلة من القاعدة المؤقتة نفسها دون إعادة الحفظ. بقيت أحداث الجولة الأصلية كما هي، بما فيها قيم الربط الفارغة القديمة؛ أثبتت اللقطة النهائية الربط الصحيح للمفتاحين بالفاتورتين. نجح الحارسان: دليل الطلبين المحفوظ في `browser-retry-reload-proxy.json`، ودليل الطلبات الثلاثة في `browser-identical-invoice-proxy.json` مع لقطات المتصفح في `browser-identical-invoice.json`. الصور في `browser-identical-invoice-screenshots/` ضمن مجلد أدلة التحقق المستبعد من Git.

شملت الجولة القيم الافتراضية نفسها في النماذج الثلاثة، لا تعديل إعدادات الضريبة. بعد التحقق أُوقف الوكيل والمشغّل المؤقت وأُعيد تشغيل API المعتاد. لم تُستخدم بيانات التطبيق أو مسارات إنتاج أو تجاوز دخول.

## حدود التغطية

- الاختبارات بمخزون اصطناعي وتكلفة شراء ثابتة وعملة SAR وشركة غير مسجلة في VAT. تبقى حالات FIFO متعددة الدفعات، تغير التكلفة قبل المرتجع، والعملات المتعددة بحاجة إلى اختبارات متخصصة.
- عكس فاتورة المورد يعكس الفوترة والقيد، ولا يعني إرجاع البضاعة فعليًا للمورد. لا يُختلق تدفق مرتجع مورد غير موجود في المنتج.
- شمل التحقق الآن إعادة تحميل الصفحة قبل تأكيد النتيجة وإعادة فتح نموذج فاتورة العميل وإعادة إدخال بياناته واسترجاع الفاتورة دون تكرار. لم يشمل بقية النماذج المالية.
- حوّل وكيل المعاينة قطع الاتصال إلى 502؛ أثبتت سجلات الوكيل الاختباري أن القطع وقع بعد نجاح الحفظ، وليس قبل إرسال الطلب. في الجولة السابقة كانت الرسالة `HTTP 502`، وفي جولة إعادة التحميل ظهرت رسالة عدم التأكد. لم تتحقق هذه الجولة من حالات الخطأ الأخرى أو سلوك إرشادات إعادة المحاولة في بقية النماذج.
- لم تُنسخ بيانات التطبيق ولم تُختبر خدمات دفع أو بريد أو OCR فعلية ولم يتم نشر للإنتاج.
