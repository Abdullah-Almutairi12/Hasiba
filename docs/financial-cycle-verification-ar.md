# التحقق من الدورة المالية وإعادة الطلب

## نتيجة هذه الجولة

نجح `pnpm verify` بجميع مراحله: فحص الأنواع، الاختبارات، بناء API والواجهات الأربع، وفحص الاعتماديات. النتيجة **343 اختبارًا ناجحًا، صفر فاشل، صفر متجاوز أو مؤجل**، بما فيها حالتا إعادة الطلب بعد استهلاك الموافقة وتغيّر قواعد الاعتماد. آخر `pnpm audit` أعاد **صفر تنبيهات في جميع درجات الخطورة** بعد دمج إصلاح الاعتماديات المنفصل. هذه نتيجة الفحوص المحددة وليست شهادة خلو النظام كله من الثغرات.

## تعريف العملية المكررة

يعرّف `Idempotency-Key` نية مالية واحدة ضمن **الشركة المصرح بها، والمستخدم، ومسار العملية**. المفتاح نفسه والبيانات نفسها يسترجعان نتيجة العملية السابقة دون إنشاء فاتورة أو حركة أو قيد جديد. إعادة المفتاح مع بيانات مختلفة ترفض بـ409. مفتاحان مختلفان يسمحان بعمليتين مشروعتين ولو كانت بياناتهما متساوية.

تُحفظ نتيجة المعاملة وبصمة المدخلات في `financial_requests` داخل معاملة PostgreSQL نفسها. قفل معاملات استشاري يسلسل الطلبات المتزامنة للمفتاح نفسه؛ فشل المعاملة يلغي بياناتها وإيصال إعادة الطلب معًا. لا تعتمد هذه الحماية على ذاكرة خادم واحد. لا يُحذف الإيصال تلقائيًا مع الزمن، لأن إعادة طلب قديم بعد حذفه قد تنشئ عملية أخرى.

المفتاح اختياري للتوافق مع العملاء السابقين. يجب على أي عميل خارجي يريد ضمان إعادة المحاولة استخدامه. لا يمكن استنتاج نية التكرار بأمان من تشابه بيانات فاتورتين.

## المسارات المغطاة

- إنشاء فواتير العملاء وعكسها وسندات القبض والإشعارات الدائنة.
- إنشاء أوامر الشراء واستلام البضاعة.
- إنشاء فواتير المورد اليدوية، واعتماد نتيجة المسح وعكس فاتورة المورد.
- إنشاء طلب نقطة البيع والحركة اليدوية للمخزون.

مسح الصورة نفسه، إرسال البريد، إنشاء رابط دفع، واستدعاءات بوابات الدفع ليست ضمن هذا الضمان. لا تتعامل الاختبارات مع بوابات حقيقية.

الإشعار الدائن يظل مسارًا على مرحلتين متوافقًا مع الاعتمادات: إنشاء مسودة محفوظة ثم الإصدار. إعادة الطلب تستأنف المسودة نفسها، وإصدارها يقفل رأسها ويرجع المستند الحالي إن كان صادرًا بالفعل. فشل الإصدار لا يترك قيدًا أو حركة مخزون جزئية، لكنه قد يترك مسودة قابلة للاستئناف. المسودات والطلبات المعلقة تحجز كمية المرتجع حتى لا تتجاوز طلبات متزامنة الكمية المباعة.

## سلوك الواجهة

`apiPost` وعميل API المولد واعتماد فاتورة المورد من المسح تستخدم `financialFetch`. يُحفظ مفتاح عشوائي مع بصمة الطلب في تخزين الجلسة، لا جسم الفاتورة أو بيانات الاعتماد. الطلبات المتزامنة المتطابقة تشترك في المفتاح. انقطاع الاتصال، وخطأ الوكيل 5xx، أو رد ناجح غير قابل للقراءة تُبقي المفتاح للطلب التالي. بعد نجاح مؤكد تصبح الإرسالية التالية عملية جديدة.

تظهر عند النتيجة غير المؤكدة رسالة تطلب إعادة المحاولة بالبيانات نفسها. إذا تعذر تخزين المفتاح لا يُرسل الطلب المالي. لا تغيّر البيانات لتجاوز رسالة الانقطاع قبل مراجعة نتيجة العملية السابقة؛ البيانات المختلفة تعني نية أخرى.

## العيوب المثبتة والإصلاحات

1. **فهرس المخزون غير متطابق:** تعريف Drizzle القديم استخدم أعمدة lot/variant القابلة للفراغ مباشرة، بينما `ON CONFLICT` في دفتر المخزون يعتمد `COALESCE`. وُحّد التعريف والترحيل مع صيغة الدفتر. إذا وجدت أرصدة تاريخية متكررة يفشل إنشاء الفهرس؛ لا تُدمج الأرصدة ولا تُحذف تلقائيًا.
2. **فحص فاتورة المورد خارج المعاملة:** كان يُنفذ قبل قفل سجل إعادة الطلب، فيرفض إعادة اعتماد فاتورة ناجحة، ويتيح التسابق على الكميات المفوترة. انتقل الفحص داخل المعاملة مع قفل أمر الشراء وجمع الكمية المطلوبة للبنود التي تعيد السطر نفسه.
3. **التسابق على إنشاء التسلسلات:** `CREATE SEQUENCE IF NOT EXISTS` وحده لا يمنع تصادم إنشاء أول تسلسل متزامن. أضيف قفل عند غياب التسلسل فقط. أرقام طلبات POS تتضمن لاحقة عشوائية بدل الاعتماد على المللي ثانية وحدها.
4. **تكرار إصدار المرتجع:** أضيف قفل رأس الإشعار وإرجاع النتيجة الحالية عند إعادة إصداره، وحجز كميات المسودات والمعلقات مع التحقق التراكمي للبنود.
5. **ترحيل تكلفة المرتجع:** إعادة المخزون كانت لا تعكس تكلفة البضاعة المباعة في الدفتر المالي. يضيف الإصدار مدين المخزون ودائن تكلفة البضاعة بقيمة حركة الإرجاع، ضمن المعاملة نفسها.
6. **قيم القيود غير الصالحة:** تُرفض قيم `NaN`/`Infinity` وسعر صرف غير موجب أو غير محدود قبل كتابة القيد.
7. **موافقة POS أحادية الاستخدام:** أصبح استرجاع نتيجة الطلب الملتزم سابقًا يسبق التحقق من الموافقة المستهلكة. الطلب الجديد لا يتجاوز فحص الموافقة، ويقفلها ويستهلكها داخل معاملة البيع نفسها.
8. **تغيّر سياسة اعتماد المرتجعات:** يُقرأ وضع الإشعار الحالي قبل إعادة تقديمه للاعتماد، ولا يمكن لتحديث حالة مشروط إعادة إشعار صادر إلى `pending_approval`. إضافة قاعدة اعتماد بعد الإصدار لا تنشئ اعتمادًا أو قيدًا أو مخزونًا جديدًا عند إعادة الطلب.

## الاختبارات

الأمر الكامل:

```bash
pnpm verify
```

اختبارات هذه الإضافة فقط، على عنقود PostgreSQL جديد ومؤقت:

```bash
pnpm test:isolated src/routes/financial-cycle.test.ts test/financial-fetch.test.mjs
```

السيناريوهات:

- أمر شراء واحد لطلبين متزامنين بالمفتاح نفسه.
- استلام البضاعة وقيد GR-IR مرة واحدة رغم إعادة الطلب.
- رفض تجميع بنود فاتورة مورد بما يتجاوز المستلم؛ إعادة استخدام المفتاح بعد فشلها تسمح بالطلب المصحح.
- فاتورة مورد مرتبطة بالاستلام، إعادة اعتمادها، وعكسها تحت طلبين متزامنين.
- بيع POS وحركاته وفاتورته وقبضه مرة واحدة.
- مرتجع مبيعات متزامن بمفتاحين مختلفين؛ قبول واحد ورفض تجاوز الكمية، وإعادة ناجحة دون زيادة المخزون.
- مصالحة رصيد المخزون المالي وCOGS في دورة التكلفة الثابتة المختبرة.
- فاتورتان متطابقتان مشروعًا بمفتاحين مختلفين؛ واسترجاع إحداهما دون تكرار، ورفض تغيير البيانات تحت مفتاحها.
- فشل بند استلام متأخر يلغي الاستلام السابق وحركته وقيده؛ وطلبان مختلفان على المتبقي لا يزيدانه.
- رفض POS ناقص المخزون دون فواتير أو قيود أو طلبات يتيمة.
- تكرار حركة مخزون يدوية.
- تساوي المدين والدائن لكل قيد مرحّل، وتراجع قيد مكتوب عند فشل معاملته الخارجية.
- رفض قيد غير متوازن وقيم مالية غير صالحة.
- قبول طلبي POS مشروعين متزامنين بأرقام مختلفة.
- إسقاط نتيجة POS الملتزم من منظور المستدعي ثم إعادة جسم الطلب ومفتاحه بعد استهلاك الموافقة: يرجع الطلب السابق دون تكرار؛ مفتاح جديد مع الموافقة المستهلكة يُرفض.
- تفعيل قاعدة اعتماد جديدة بعد إصدار مرتجع ثم إعادة طلبه مرتين: تبقى حالته وقيده والمخزون وعدد طلبات الاعتماد كما كانت.
- اختبارات النقل للواجهة: التزامن، انقطاع الاتصال، 5xx، رد ناجح تالف، وانعدام تخزين الجلسة.

التقارير الفعلية وأعداد النجاح/الفشل/التجاوز في:

- `generated-artifacts/verification/summary.json`
- `generated-artifacts/verification/tests.json`
- سجلات المراحل في المجلد نفسه.

ملف اختبارات النقل بصيغة JavaScript خارج مشروع TypeScript الخاص بالخادم، ليظل الكود ذو أنواع DOM ضمن مشروع عميل الويب الصحيح. كود النقل نفسه يبقى TypeScript ويخضع لفحص مكتبة العميل؛ لم يُعطل فحص أنواع التطبيق.

## حدود التغطية

- الاختبارات بمخزون اصطناعي وتكلفة شراء ثابتة وعملة SAR وشركة غير مسجلة في VAT. تبقى حالات FIFO متعددة الدفعات، تغير التكلفة قبل المرتجع، والعملات المتعددة بحاجة إلى اختبارات متخصصة.
- عكس فاتورة المورد يعكس الفوترة والقيد، ولا يعني إرجاع البضاعة فعليًا للمورد. لا يُختلق تدفق مرتجع مورد غير موجود في المنتج.
- فحص المتصفح دخل إلى نموذج فاتورة العملاء لكنه لم يرسل فاتورة: تجهيز الجولة الأولى لم يتضمن منتجات والنموذج يتطلب اختيار منتج. أُضيف منتج إلى تجهيز المتصفح المستقبلي؛ إنشاء الفاتورة من الواجهة وإعادة رد ناجح مفقود لم يُثبتا في هذه الجولة. أداة المتصفح لا تدعم إسقاط الرد بعد تنفيذه؛ هذا السيناريو مغطى باختبارات النقل وباختبارات HTTP على الخادم.
- لم تُنسخ بيانات التطبيق ولم تُختبر خدمات دفع أو بريد أو OCR فعلية ولم يتم نشر للإنتاج.
